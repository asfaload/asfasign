# About

Asfaload is an open source project delivering a generalised multi-signature sign-off solution.

It is:

* open source
* self-hostable
* auditable
* easy to use
* accountless (the secret key is the identity)
* using existing cryptographic libraries

It is a work in progress that will soon reach a usable state.

It aims to secure the download of artifacts from Github (and others) releases, by requiring the signature of a release by multiple
authorised parties. It provides configurable m-of-n signature thresholds to be enforced before the release of a signature is considered as complete.

# Use of LLMS

* Is this vibe-coded? No
* Is it using LLM assistance? Yes

The use of LLMs evolved during the project, and you can read details about this in a [blog post](https://www.asfaload.com/blog/ai_use/).

In [core/](https://github.com/asfaload/asfaload/tree/master/core), the libraries code has been written by a human, and when LLMs were used it was mainly to generate the tests.
This is kept this way, with all code thoroughly reviewed.

In [client-lib/](https://github.com/asfaload/asfaload/tree/master/client-lib) and in [rest-api/](https://github.com/asfaload/asfaload/tree/master/rest-api)
LLMS have been used more extensively for the apps code. As I learn how to optimally use LLMs for code production, my usage pattern has evolved during the project.
I want to balance speed of development and still mastering the code of the solution. The optimal approaches currently seem to be either a spec-driven approach with
small incremental steps, or writing a skeleton of code and letting the LLMs complete the gaps.

There is no commit by an agent user, for two reasons:

* If an agent commits locally during development, the code is reviewed and often thoroughly modified and rearranged by a human.
* I don't want to push unreviewed code to the repo, so I have set up a git hook refusing to push commits done by an LLM agent.
